# قانونِ سختِ ممیزیِ Neura (Audit Rulebook)

این سند «دانشِ ممیزی» است. هر باگی که از قلم افتاد، به‌صورتِ یک **قانون** اینجا اضافه می‌شود تا **تکرار نشود**.
قبل از اینکه هر واحد «تمام» اعلام شود، باید همهٔ قوانینِ مربوطه رعایت شده باشد. ادعای «درست شد» بدونِ
**شواهد** (اسکرین‌شاتِ رِندرِ واقعی + تستِ بک‌اندِ واقعی) ممنوع است.

## روشِ کار (غیرقابلِ‌مذاکره)
1. **واحدهای کوچک، تا ته.** یک تب/بخش در هر نوبت؛ هر دکمه، تب، منو، مودال و **جریانِ تودرتو** از اول تا آخر.
2. **با چشمِ واقعی.** هر حالت را رِندر کن، اسکرین‌شات بگیر، و **خودت نگاه کن** — نه فقط چک‌کردنِ وجودِ DOM.
3. **بک‌اندِ واقعی + دادهٔ واقعی.** روی Postgres واقعی و سرورِ واقعی؛ نه stubِ فیک.
4. **سه‌گانهٔ راستی‌آزمایی:** کد + رِندرِ واقعی + رفتارِ بک‌اند. اگر هر سه هم‌خوان نبودند، هنوز تمام نشده.
5. **بعد از هر تغییر**، صفحه‌های متأثر را دوباره رِندر و بصری چک کن (رگرسیون‌گیری).

## قوانین (از باگ‌های واقعیِ این پروژه)
- **R1 — قابلِ‌کلیک ≠ کارکردن.** هر المانِ قابلِ‌کلیک باید **واقعاً باز/اجرا شود** و نتیجه‌اش **دیده شود**. «در DOM هست» کافی نیست.
- **R2 — دیده‌شدن (z-index/پرتال).** منو/مودالی که باز می‌شود باید **روی محتوا** بنشیند، نه پشتش. عناصرِ `absolute` که ممکن است زیرِ کارت‌ها بروند → **پرتال به body + fixed**. [باگ: کشوییِ دستیار پشتِ کارت‌ها پنهان بود]
- **R3 — همهٔ نقش‌ها.** منطقِ نقش‌محور (`role==='user'` و …) را با **admin و user هر دو** تست کن. [باگ: نمونهٔ دستیار فقط برای user بسط می‌شد؛ برای admin نه]
- **R4 — مسیرِ به‌دست‌آوردن باید وجود داشته باشد.** اگر UI یک قابلیت را نشان می‌دهد (سوییچرِ چند-نمونه)، باید راهِ واقعیِ ساختن/خرید هم باشد. [باگ: سوییچرِ چند-دستیار بود ولی خریدش نبود]
- **R5 — Hooks پیش از هر return.** هیچ `useState/useEffect` بعد از `if(...) return null` نگذار. [باگ: کرشِ سفیدِ چت، React #310]
- **R6 — رِندرِ امنِ داده.** آرایه/آبجکت را مستقیم به‌عنوان فرزندِ React رِندر نکن. [باگ: کرشِ سفارشاتِ داین، React #31]
- **R7 — بدونِ fallbackِ فیک.** الگوی `real > 0 ? real : [hardcoded]` ممنوع؛ خالی، خالی نشان داده شود. [باگ: CRM 45/28/18/12 ویترینی]
- **R8 — ماندگاری واقعی.** فرم/خرید بعد از ثبت باید با **خواندنِ دوباره از DB** تأیید شود، نه toastِ خوش‌بینانه.
- **R9 — تبِ فعال، دکمهٔ مرده نیست.** کلیکِ تبِ ازقبل‌انتخاب‌شده = no-opِ درست؛ آن را «مرده» گزارش نکن (تلنگرِ حالت بزن).
- **R10 — ماژولی/مشترک.** رفتارِ مشترک (خرید/چت/…) در **یک ماژول/کامپوننت** باشد تا تغییر یک‌جا همه‌جا اعمال شود.
- **R11 — سوپرادمین را واقعاً چک کن.** پنلِ سوپرادمین اپِ جداست؛ ادعای «چک کردم» بدونِ رِندرِ واقعیِ صفحه‌هایش ممنوع.
- **R12 — صداقت.** اگر چیزی را تست نکرده‌ای، بگو «تست نکردم». هیچ‌وقت «درست شد» بدونِ شواهد نگو.
- **R13 — سوپرادمین واحدِ درجه‌یکِ ممیزی است.** پرباگ و پرِ فیک است. برای **هر تنظیم/فیچرِ سوپرادمین** باید مشخص شود:
  (الف) به کجای اپ **وصل** است یا نه، (ب) داده‌اش **واقعی** است یا فیک. یک **نقشهٔ اتصال (wiring map)** ساخته و
  نگه داشته شود تا بعداً دوباره‌کاریِ «ببینیم به کجا وصل است» نشود. همهٔ فیک‌ها باید واقعی/حذف شوند.
- **R14 — تنظیمِ تکراری ممنوع.** یک تنظیم نباید در **چند بخش به شکل‌های مختلف** تکرار شود (به‌ویژه در سوپرادمین).
  هر تنظیم **یک منبعِ حقیقتِ واحد** دارد؛ تکراری‌ها ادغام/حذف شوند تا دوباره‌کاری و ناهم‌خوانی نشود.
- **R15 — امکاناتِ ناقص را کامل کن.** هر جا فیچری **امکاناتِ کامل ندارد** (مثلِ گروه که اصلاً تنظیمات نداشت)، باید
  **تکمیل** شود — نه اینکه از کنارش رد شوی. «هست ولی نصفه» = ناقص = باید کامل شود.
- **R16 — معیار: لیدرهای بازار (و بهتر از آن‌ها).** هر فیچر را با **لیدرهای بازار** بسنج (چت/گروه/تماس ← تلگرام و
  واتس‌اپ؛ فروش/CRM ← ابزارهای مرجع؛ …). امکاناتِ ما باید **دستِ‌کم برابر و ترجیحاً کامل‌تر/بهتر** باشد.
  فهرستِ امکاناتِ لیدر را بنویس، شکاف را مشخص کن، و پُرش کن. [مثال: تنظیماتِ گروهِ فعلی ~۲٪ِ تلگرام است ⇒ باید تکمیل شود]
- **R17 — سیم‌کشی (wiring) دقیق و کامل.** برای هر بخش باید **مسیرِ کاملِ داده** مشخص شود: **از کجا می‌آید و به کجا می‌رسد**
  — بینِ ایجنت‌ها و بینِ ایجنت↔سوپرادمین. هر تنظیمِ سوپرادمین باید به همان بخشِ اپ **وصلِ واقعی** باشد و برعکس.
  هر بخشِ UI که تکمیل شد، **counterpartِ سوپرادمینش هم همان‌جا** تکمیل/سیم‌کشی شود تا بعداً دوباره‌کاری نشود و
  در پایان، «اضافاتِ سوپرادمین» طبیعتاً روشن شوند. نقشهٔ سیم‌کشی ثبت و نگه‌داری شود.
- **R18 — «چشمِ بینا»: کلِ صفحه را ببین، نه فقط بالای فولد.** [باگ: تب‌های خانه بارها دیده نشدند]
  علتِ ریشه‌ایِ ندیدن ۵ مورد بود و هر ۵ در ابزارِ ممیزی رفع شد:
  0. **[علتِ اصلی] مودالِ مسدودکننده روی صفحه**: یک مودالِ «دسترسی به میکروفون و دوربین» هنگامِ ورود به خانه باز می‌شد و
     `backdrop-blur`ِ آن **کلِ صفحه را تار/پوشیده** می‌کرد؛ برای همین همهٔ اسکرین‌شات‌های خانه یک تصویرِ محوِ ناخوانا بودند
     و تب‌ها اصلاً دیده نمی‌شدند → حالا پیش از عکس، هر اورلیِ مسدودکننده (بعداً/بستن/Escape) **بسته** می‌شود.
  1. **اسکرین‌شاتِ غیر-fullPage**: عکس فقط ۸۴۴px نخست را می‌گرفت؛ خانه اسکرول‌شونده است و هر تب/بخشِ **زیرِ فولد**
     در عکس بریده می‌شد → حالا `screenshot({ fullPage: true })` + **اسکرولِ کاملِ صفحه** پیش از عکس.
  2. **فقط ویوپورتِ موبایل ۳۹۰px**: کاربر گاهی لِی‌اوتِ عریض‌تر (~۸۲۱px) را می‌بیند که محتوای بیشتری نشان می‌دهد →
     حالا **دو پاس**: موبایل ۳۹۰ **و** دسکتاپ ۱۰۲۴، هر دو fullPage.
  3. **برشِ برچسبِ بلند (>۴۰ نویسه)**: کارت‌های چندخطیِ خانه (لیبل+زیرلیبل+قیمت) از فهرستِ کلیک‌پذیرها **حذف** می‌شدند →
     حالا «خطِ نخست» برچسب می‌شود و سقف ۸۰ نویسه؛ کلیک‌گر هم با همین نرمال‌سازی هدف‌گیری می‌کند.
  4. **سقفِ ۱۸ دکمه در هر صفحه**: تب‌های بعد از دکمهٔ ۱۸ام هرگز شمرده نمی‌شدند → سقف به ۶۰ رسید.
  علاوه بر ابزار: **تمِ رِندر** را هم چک کن — خانه دو پیاده‌سازیِ کاملاً متفاوت دارد (`EuHomeScreenGlass` برای glass/dark و
  `EuHomeScreenDefault` برای بقیه)؛ ممیزی باید **هر دو تم** را ببیند وگرنه نیمی از UI نادیده می‌ماند.

## چک‌لیستِ هر واحد (قبل از «تمام»)
- [ ] هر تبِ داخلِ این بخش باز شد و محتوا/کرش/سفیدی چک شد؟
- [ ] هر دکمه/منو/مودال باز شد و نتیجه‌اش **دیده** شد (اسکرین‌شات)؟
- [ ] اسکرین‌شاتِ **fullPage** (نه فقط بالای فولد) + اسکرولِ کامل + **هر دو ویوپورت** (موبایل/دسکتاپ) + **هر دو تم**؟ (R18)
- [ ] جریان‌های تودرتو تا **آخر** رفته شد (نه فقط سطحِ اول)؟
- [ ] با هر دو نقشِ user و admin (در صورتِ ربط) تست شد؟
- [ ] داده‌ها از بک‌اندِ واقعی‌اند (نه فیک/هاردکد)؟ ماندگاری با DB تأیید شد؟
- [ ] **امکانات کامل است؟** با **لیدرِ بازار** (تلگرام/واتس‌اپ/…) مقایسه شد و شکاف پُر شد؟ (R15/R16)
- [ ] **تنظیمِ تکراری** نیست؟ هر تنظیم یک منبعِ واحد دارد؟ (R14)
- [ ] اگر بخشی از **سوپرادمین** است: نقشهٔ اتصال (وصل/نه، واقعی/فیک) ثبت شد؟ (R13)
- [ ] رگرسیون‌گیری بعد از تغییر انجام شد؟
- [ ] هر باگِ نو به‌عنوانِ قانونِ جدید به همین فایل اضافه شد؟

## واحدهای سوپرادمین (R13 — باید یکی‌یکی و کامل ممیزی شوند)
پنلِ سوپرادمین ۳۳ صفحه دارد. هر کدام یک واحد است؛ برای هرکدام «نقشهٔ اتصال + واقعی/فیک + تکمیل + بدون‌تکرار»:
داشبورد، کاربران، ایجنت‌ها، کسب‌وکارها، چت‌ها، مشتریان، تراکنش‌ها، کیف‌پول‌ها، فاکتورها، تنظیماتِ ایجنت‌ها
(منشی/بازاریابی/مالی/تدارکات/صندوقدار)، تیکت‌ها، QC، درخواستِ تماس، خبرنامه، AI، VoIP، ردیاب، پلن‌ها،
تنظیماتِ کلی، ظاهر، زبان‌ها، پیکربندی، نقش‌ها، ادمین‌ها، لاگ‌ها.

> هر بار که باگی از قلم افتاد، **اول** قانونش را اینجا اضافه کن، **بعد** رفعش کن.
